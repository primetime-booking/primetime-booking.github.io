# Восстановление перехода с GitHub Pages при сбое PWA-кэша — v7

- Цель: не допускать `ERR_FAILED` на `primetime-booking.github.io/` при доступной сети и отказе CacheStorage.
- Сделано: worker v7 активируется даже при неполном precache, сохраняет старый полный офлайн-кэш и отдаёт доступную сетевую навигацию при ошибке кэша; версии HTML, site-update.js и SW согласованы. Коммит `4ce7183`.
- Проверено: статический и сценарный тесты SW, проверки маршрута и booking-flow, все три CI успешны; живые SW и HTML показывают v7, корневой URL перенаправил на `/r/ramil`, профиль открылся после F5 во встроенном браузере.
- Текущий этап: опубликовано на GitHub Pages.
- Следующие шаги: подтвердить обычный F5 с исходного адреса в проблемном Chrome-профиле.
- Зафиксированные решения: CacheStorage, IndexedDB и пользовательские записи не очищать.
- Ограничения и блокеры: исходный Chrome-профиль агенту недоступен; сообщение пользователя об открытии сайта ещё не подтверждает повторный F5.

# Цель

Перенести клиентский PrimeTime в независимый публичный GitHub Pages `primetime-booking/primetime-booking.github.io`, не затрагивая PrimeTime Pro и «Анатомию массажиста».

# Сделано

- Создан отдельный публичный репозиторий организации.
- Перенесены клиентские страницы и необходимые общие зависимости из `minuta-online-booking/`.
- Добавлены отдельные manifest, service worker/cache и Pages workflow.
- Добавлены независимые браузерные проверки источников привлечения и восстановления групповой записи.
- В «Моих записях» явно показано восстановление на другом устройстве по номеру телефона и личному коду из сохранённого после записи файла.
- Если вход по SMS недоступен, форма восстановления раскрывается автоматически; SMS и другие внешние уведомления не отправляются.
- Корневой адрес Pages направляет обычный вход прямо в опубликованный профиль Рамиля `/r/ramil`; явные ссылки записи остаются в fail-closed booking-flow.
- Service worker v6 при активации обновляет только уже открытую корневую оболочку, чтобы старый PWA-кэш не оставлял пользователя на прежней странице; deep links и запросы не перехватываются.

# Зафиксированные решения

- Старый адрес тренажёра `anatomy-trainer/#/home` не изменяется.
- Кабинет исполнителя остаётся в исходном репозитории; клиентские ссылки на него ведут на прежний адрес.
- Используется существующий публичный Supabase backend без service-role ключей и изменений данных.
- Старый клиентский адрес ведёт через короткий Pages-адрес в тот же каталог; сохраняются только поддержанные attribution/profile параметры, служебный `#/home` и неизвестные параметры отбрасываются.
- Явные параметры `org`, `service`, `provider`, `location` или `group` сохраняют прямой защищённый booking-flow вместо отправки в общий каталог.

# Ограничения и блокеры

- Компактные RPC v165 ещё отсутствуют в production-БД; опубликованный клиент корректно использует fallback v101.
- Production-миграция не применялась: в текущей задаче не было разрешения и подтверждённого доступа для изменения базы.
- Каталог остаётся серверным приложением Workers/D1/R2; Pages отвечает за короткий входной маршрут и не дублирует серверные данные.
